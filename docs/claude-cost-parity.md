# Claude Code ↔ LLM Usage: стоимость через корпоративный прокси

## Дополнение 1.6.4 — итоги `cost-state`, заглушки субагентов и TTL из стоимости

Четыре диагностических архива 1.6.3 (Claude Code 2.1.280) и структурный дамп журналов показали: во всех случаях `/usage` равен сумме `cost_usd` уникальных API-событий сессии, а приложение теряло 29–42 % на субагентах.

| Сессия | `/usage` | 1.6.3 | Потеря |
|---|---:|---:|---|
| 1 | $8.923245 | $5.23 (виджет $4.38) | 14 заглушек и 4 отсутствующих вызова с записью кэша |
| 2 | $16.065282 | $11.20 | 42 заглушки, 1 вызов |
| 3 | $3.090241 | $2.20 | все 7 шагов субагента — заглушки |
| 4 | $32.39 | $16.53 | 18 + 7 вызовов; телеметрии нет за первые 30 минут |

Причины:

1. **Заглушки субагентов.** Claude Code пишет фрагменты ответа субагента с `usage` из четырёх нулевых полей без `stop_reason`, `speed` и `service_tier` и часто не дописывает итоговую строку. Это не ноль, а отсутствие счётчиков. В трёх сессиях заглушками были 100 %, 89 % и 83 % строк субагентов.
2. **Отказ восстанавливать запись кэша.** Телеметрия не содержит TTL, поэтому любой вызов с `cacheWrite > 0` отбрасывался. Под это попали почти все шаги субагентов.
3. **Итог сессии отбрасывался.** Claude Code 2.1 пишет строки `type: "cost-state"` с накопленным `modelUsage` при выходе и продолжении сессии; значения совпадают с `/usage` до токена (в т. ч. промежуточный итог $6.991981 = сумма телеметрии до него). Проверка требовала равенства cache read/write с журналом и разницы input/output < 200k, а заглушки делают это невозможным. Без времени у строки итог ещё и блокировал всю телеметрию модели.

Решение:

- `TranscriptUsageParser.isPlaceholder`: заглушка помечает запрос `countersUnknown`. Реальные счётчики, включая настоящий ноль, всегда заменяют заглушку и не заменяются ею. Неразрешённые заглушки дают причину `countersMissing` и пометку неполноты, а не $0.
- `ClaudeSessionAccounting`: каждый итог закрывает сегмент. Запросы своего файла упорядочены позицией, субагентов — временем относительно первой строки после итога. Остаток `итог − предыдущий итог − журнал сегмента` по всем четырём счётчикам добавляется как служебный запрос с интервалом сегмента, поэтому продолженная сессия делится по дням (сессия 2: $16.065282 за первый день, $43.2710545 итог). Сброс счётчика после продолжения принимается как новый отсчёт; необъяснимый сегмент остаётся неполным, а следующие сравниваются с ним. Пустой `modelUsage`, модели только фоновых вызовов и повторные итоги поддерживаются.
- `ClaudeCacheTTL`: разбивка 5m/1h решается из стоимости Claude по тарифам отчёта (1h = явная ставка или 2 × input). Для телеметрии — из `cost_usd` вызова, для остатка итога — из разницы его стоимости и запросов сегмента. Без однозначного решения телеметрия остаётся консервативной, а остаток итога получает раскрытый 5m fallback; агрегат многоуровневого тарифа выше 200k помечается неполным.
- Покрытие итогом: запросы сегмента помечены `snapshotCovered`; события без запроса проверяются по сегментам, а промежуток между итогом и следующей строкой журнала считается неоднозначным.
- Дневной расчёт читает журналы субагентов так же, как CLI и чат; идентификатор движка `telemetry-accounting-3` пересчитывает кэш итогов.

Пользовательские тарифы и исключения моделей по-прежнему применяются: `costUSD` итога используется только для TTL. Сессия без итога и без телеметрии с заглушками показывается как нижняя граница с причиной.

Проверки: обезличенные фикстуры `claude-telemetry-sessions.json` (четыре архива, даты сдвинуты) и `claude-cost-state.json` (три сессии: одиночная, продолженная, со сбросом счётчика); сценарии в `ClaudeAccountingScenarios` и `ClaudeTelemetryAccountingScenarios`, включая дневной отчёт и чат с реальным helper.

## Дополнение 1.6.2 — восстановление по API-телеметрии

Новая числовая регрессия: в учёте 1.6.1 сохранено $14.0709776; 114 запросов имеют неполные/нулевые счётчики, 84 API-запроса отсутствуют, ещё один служебный запрос стоит $0.003888. По доступной телеметрии и непересекающимся ранним JSONL-запросам восстанавливается $28.8634092: input 2 406 979, output 444 252, cache read 51 752 266, cache write 0. Это подтверждённый итог имеющихся данных, а не доказательство точного совпадения с округлёнными $28.87: начало сессии не покрыто телеметрией. Исходные секретные журналы не требуются и не включены в фикстуру.

Сводка в обоих режимах и детализация используют общий `ClaudeTelemetryAccounting`. Уникальные успешные API-события дополняют неполный запрос по session/request/client ID либо создают отдельный учётный запрос без выдуманной привязки к сообщению. Вспомогательные вызовы также учитываются. Стоимость события не копируется: все токены оценивает прежний helper с тарифами отчёта, включая пользовательские настройки и исключения моделей. Перед заменой дневного итога исходные счётчики сверяются с CLI; результат заменяется целиком только после проверки ответов helper.

Повторные события не начисляются повторно. Ошибки, конфликтующие ID/модели/положительные счётчики, отсутствующие время или speed, возможные дубликаты requestless-записей и неизвестный TTL положительного cache write не дают неподтверждённых добавлений. Валидный cumulative `modelUsage` уже владеет покрытыми вызовами; без явного времени snapshot его граница не угадывается. Неоднозначность сохраняет признак неполноты. Исправленный запрос остаётся в своём исходном дне, дополнительный относится к дате API-события.

Телеметрия остаётся локальной и добровольной; используются уже сохранённые события даже при выключенном приёмнике. Восстановление зависит от их наличия и срока хранения. Без них первичную потерю данных в JSONL этот механизм не исправляет. В диагностическом экспорте `missingCounters`, `telemetryRecovery` и `transcriptCountersBeforeRecovery` сохраняют различие между неизвестными/нулевыми и восстановленными счётчиками. Сравнение после восстановления может включать счётчики из самой телеметрии. Версия Swift-этапа включена в идентификатор движка, чтобы прежний кэш итогов пересчитался.

Проверки: `bash Scripts/check-claude-accounting.sh --cli /absolute/path/to/ccusage`; полный CI также запускает XCTest и реальный bundled helper. Фикстура содержит только числа и новые синтетические ID/времена/тексты.

Обновлено: 2026-10-07. **Исправления расчёта первоначально подготовлены как 1.5.5 в [PR #29](https://github.com/RunGuitarMan/llm-usage-widget/pull/29). Вместе с локальной телеметрией они входят в выбранную пользователем поставку 1.6.1.**
Единый источник знаний сессии: устаревшие выводы заменяем, ограничения сохраняем. OpenSpec: proposal → evidence → requirements/scenarios → design → tasks.

## Proposal — цель

Устранить потерю cache write, случайный Batch-тариф и пропуск служебных расходов. Сверять токены и сохранённые итоги, не подгонять цену множителем. `/usage` и телеметрия отражают оценку Claude Code с предупреждением unknown models, а не подтверждённый счёт провайдера.

## Requirements / scenarios — реализовано

- **R1, cache write:** отсутствующая/пустая/нулевая TTL-разбивка сохраняет положительный aggregate; используется прежний fallback 5m. Ненулевая разбивка остаётся приоритетной; aggregate повторно не складывается. Противоречие ненулевых значений отмечается в детализации. Сценарий 133835 + нулевые TTL даёт write **$0.3345875**; отдельный тест сохраняет ставку 1h.
- **R2, тариф:** fuzzy-поиск не пересекает границу обычного и `:batch` ключа. Явный Batch и пользовательские overrides сохраняются. R1+R2 дают **$1.3015691** для 24 основных запросов.
- **R3, полный итог:** валидный накопительный `modelUsage` восстанавливает только разницу input/output после сверки основных токенов. Повторные snapshots заменяют предыдущую разницу; новые основные запросы после snapshot сохраняются. Сценарий новой сессии даёт **$1.3084091** без двойного учёта.
- **R4, согласованность:** сводка в обоих режимах и детализация чата используют тот же helper и тарифы. Сохранённый `costUSD` не подменяет пользовательский расчёт; тест с удвоенными тарифами удваивает всю сумму. Новый контракт движка инвалидирует несовместимые результаты и тарифные квитанции.

## Design — реализация и ограничения

- Helper **20.0.26-llmusage.4**, **contractVersion=3**; upstream commit остаётся `d9821088b98aa536c7a385aa1a4579d6fa02269b`. Изменения `types.rs`, `cost.rs`, `pricing.rs` закреплены патчем и SHA-256 в `Configuration/Dependencies.json`. Отдельно установленный терминальный ccusage автоматически не обновляется.
- Swift `ClaudeResponseIdentity` / `TranscriptUsageParser` сохраняют cache write. Для нулевого/пустого вложенного TTL показывается пояснение о 5m fallback.
- `ClaudeSessionAccounting` проверяет корневой `modelUsage` по структуре, session ID и предшествующим дедуплицированным запросам. Исходный `type` metadata сборщик заменил на `other`, поэтому реализация от него не зависит. Алиасы `[1m]` сопоставляются с исходной моделью запроса; для тарификации используется исходное имя.
- `ClaudeAccountingService` сверяет основные дневные токены с CLI и оценивает подтверждённые служебные токены одним дополнительным изолированным offline-вызовом helper. Передаются только тарифные настройки, без фильтров дат и путей. `~/.claude.json` не используется: последний итог проекта может быть перезаписан.
- Служебные токены показываются отдельно, без привязки к случайному сообщению и без выдуманного числа API-вызовов. Cumulative overhead через полночь остаётся в итоге всего чата; дневной итог его не распределяет наугад и отмечает неполноту.
- Чужой session ID, неоднозначные модели, уменьшение накопительного остатка, несовпавший cache, web-search расходы, fast-режим или слишком большой остаток не принимаются молча. Невалидные/неоднозначные данные отмечаются как неполные. Без snapshot показывается доступный transcript-расчёт, служебные центы не выдумываются; точное совпадение всех исторических сессий не гарантируется.
- Проверены два предоставленных набора чисел. Формат всех будущих версий Claude и реальный счёт корпоративного прокси не заявляются проверенными. Постоянная телеметрия для сессий с валидным snapshot не требуется.
