# Замена ccusage собственным сборщиком статистики

Оценка на 29 сентября 2026 года. Исследован ccusage **v20.0.26**, commit `d9821088b98aa536c7a385aa1a4579d6fa02269b`, и текущая рабочая версия LLM Usage. Это оценка реализации, а не уже выполненная замена.

**Вывод:** собственный сборщик на Swift реалистичен. Для Claude Code, Codex и Gemini это отдельный проект на несколько недель. Сохранение всех 18 источников требует нескольких месяцев и постоянного сопровождения форматов. Основная сложность — достоверность подсчёта, а не подключение к интерфейсу.

**Что уже есть в приложении**

- `LLMUsage/Services/CCUsageService.swift` изолирует запуск CLI за `CCUsageServing`. В текущем рабочем варианте есть режимы `claudeOnly` и `allAgents`; общий отчёт дополняется корректным отдельным запросом Claude.
- `LLMUsage/Shared/UsageModels.swift` содержит собственные модели `UsageSession`, `TokenUsage`, `UsageSnapshot`, группировку по источникам и моделям, стабильные идентификаторы и календарные границы `UsageDay`.
- `LLMUsage/App/UsageStore.swift` уже отвечает за обновления, кэш и загрузку истории. `RefreshSchedule` переключает частоту; стандартный быстрый интервал — 5 секунд.
- `SnapshotStorage`, виджеты, графики и большая часть интерфейса получают готовые снимки и не нуждаются в ccusage непосредственно.
- `TranscriptService` самостоятельно читает переписки из JSON, JSONL и SQLite. От него можно переиспользовать отдельные знания о путях и форматах. Его подсчёт статистики не заменяет: он ищет выбранный чат, может предпочитать один из журналов и загружает записи целиком, с пределами на размер и число файлов.

Таким образом, переписывать всё приложение не требуется. Заменить нужно сервис сбора и декодер ответа CLI, изменить диагностику и настройки, обновить контекст кэша и инструкцию установки.

**Что фактически делает ccusage**

Текущая версия использует нативное ядро на Rust; npm-пакет запускает платформенный бинарник. Переносить терминальные таблицы, парсер CLI, все команды и все параметры конфигурации нашему приложению не нужно. Но потребуется собственная реализация поиска источников, чтения usage-событий, нормализации, устранения повторов, фильтрации времени и расчёта стоимости.

В `rust/adapters` 18 источников и отдельный общий модуль: Claude, Codex, Gemini, OpenCode, Amp, Droid, Codebuff, Hermes, pi, Goose, Kilo, Copilot, Antigravity, Kimi, Qwen, OpenClaw, Grok и ZCode. Это существенно шире трёх основных агентов из описания приложения.

**Claude Code — средняя сложность**

Базовые записи JSONL просты: время, сессия, модель и категории токенов. Трудная часть — повторные записи одного ответа, скопированные транскрипты, подагенты и записи `agent_progress`. Идентичность ответа зависит от сочетания session/message/request ID и иногда timestamp; одной проверки уникальности `message.id` недостаточно. Есть вложенные вызовы advisor с отдельной моделью и стоимостью. Данные кэша могут различать создание на 5 минут и на час.

Нужно восстанавливать и устранять повторы до агрегации, затем ограничивать отдельные события интервалом `[начало дня, начало следующего дня)` в выбранном часовом поясе. При этом контекст для устранения повторов может находиться за пределами выбранного дня.

Источники: [Claude loader и дедупликация](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/adapters/claude/src/lib.rs), [поиск файлов](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/adapters/claude/src/paths.rs).

**Codex — высокая сложность**

Нужно поддержать `sessions` и `archived_sessions`, восстановление модели из контекста, события `token_count`, значения `last_token_usage` и накопительные `total_token_usage`. Суммировать все накопительные значения нельзя. Повторное событие с неизменным счётчиком не должно добавлять расход.

Кэшированные токены являются частью входных, а reasoning-токены — частью выходных: нормализация должна предотвращать двойной учёт. История, перенесённая в fork или подагента, не всегда является новым расходом. ccusage сопоставляет её с родительским журналом, а при отсутствии исходных данных применяет эвристики. Для нового сборщика нужно явно определить поведение при недостаточных данных, не обещая точность, которой нет в журнале. Дополнительно есть переключения модели, режима Fast/service tier и правила длинного контекста.

Источники: [парсер и восстановление счётчиков](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/adapters/codex/src/parser.rs), [история fork-сессий](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/adapters/codex/src/replay.rs), [нормализация токенов](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/adapters/codex/src/types.rs).

**Gemini — умеренная дополнительная работа**

Есть JSON и JSONL, несколько вариантов названий полей и размещения статистики. Требуются правила для cached input, thoughts и tool tokens. После готового общего движка этот адаптер заметно меньше Codex.

Источник: [Gemini parser](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/adapters/gemini/src/parser.rs).

**Остальные источники неоднородны**

OpenCode читает старые JSON-хранилища и новые SQLite-схемы, включая границы скопированной истории fork. Antigravity требует разбора SQLite и бинарных protobuf-полей. Hermes читает итоговые счётчики сессий из базы. Поэтому дополнительные источники нельзя оценивать как одинаковые небольшие JSON-парсеры.

У некоторых форматов есть только итог сессии, без времени каждого расхода. Восстановить точное распределение по дням из такого итога невозможно; потребуется явно показывать ограничение данных. Повторить выдачу ccusage и обеспечить корректную дневную статистику — разные критерии.

Источники: [OpenCode](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/adapters/opencode/src/loader.rs), [Antigravity](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/adapters/antigravity/src/parser.rs), [Hermes](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/adapters/hermes/src/loader.rs).

**Цены — самостоятельный модуль**

ccusage использует LiteLLM и models.dev, встроенные снимки тарифов, сопоставление имён моделей, разные тарифы кэша, множители Fast и пороги длинного контекста. HTTP-часть проверяет обновления через ETag. Это больше, чем словарь «имя модели → две цены».

Для нашей реализации предлагается встроенный каталог поддерживаемых моделей плюс фоновое обновление с проверкой формата и сохранением последней пригодной версии. Офлайн-запуск должен работать с первого открытия. Неизвестная модель должна сохранять токены и помечать стоимость как неполную; существующее поле `costIsIncomplete` подходит для представления результата. Стоимость рассчитывается на уровне запроса, где известны его параметры, а затем суммируется.

Данные для расчёта и версия тарифов должны позволять пересчитать суммы без повторного чтения всей переписки. Нужно заранее определить политику: переоценка истории по текущему каталогу или исторические ставки при наличии достоверных дат их действия. Полная историческая тарификация не входит в базовую оценку ниже.

Источники: [каталог и сопоставление моделей](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/crates/ccusage-core/src/pricing.rs), [расчёт](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/crates/ccusage-core/src/cost.rs), [HTTP-кэш](https://github.com/ccusage/ccusage/blob/v20.0.26/rust/crates/ccusage/src/http.rs).

**Предлагаемая архитектура**

`LocalUsageService` на Swift за общим протоколом `UsageServing` сохраняет внешний результат `UsageSnapshot`. Внутри — отдельные адаптеры источников, нормализованные usage-события, общий каталог цен и индекс файлов. Внутреннее событие должно хранить больше, чем нынешний итог `TokenUsage`: идентичность запроса, время, параметры кэша, режим тарификации и происхождение данных.

Первый полный проход строит индекс. Последующие обновления используют кэш разбора и перечитывают изменившиеся файлы; оптимизацию до чтения только дописанного хвоста можно добавить после проверки поведения повторных/исправленных записей. Требуются обработка усечения и замены файла, неполной последней строки, появления родительского журнала и смены версии парсера. Полное чтение всех логов каждые 5 секунд нежелательно.

Текущий день и семь дней истории должны строиться из одного обновлённого индекса, а не инициировать отдельный полный обход для каждой даты. Виджет продолжает читать маленький готовый снимок и сам не сканирует логи.

Вместо пути к ccusage в настройках нужны источники, папки журналов и понятная диагностика: «нет данных», «папка недоступна», «часть файлов не распознана». Явный выбор папок решает и проблему переменных, заданных только в Terminal. В контекст кэша нужно добавить набор папок/источников и версию вычислений, сохранить стабильные ID сессий и пересчитать старую историю, чтобы не смешивать результаты разных алгоритмов.

**Оценка трудоёмкости**

Это инженерная оценка работы одного разработчика, знакомого с Swift и проектом, с доступом к репрезентативным тестовым журналам. Рабочие дни включают реализацию, проверки и интеграцию; строки таблицы — суммарные альтернативы, их не нужно складывать. Оценка не является обещанием календарного срока.

| Объём самостоятельной реализации | Оценка | Уверенность |
|---|---:|---|
| Только Claude: токены, стоимость, дни, сессии, история, настройки и проверка на двух Mac | 7–12 рабочих дней | Средняя |
| Claude + Codex + Gemini, с общим каталогом цен, индексом и регрессионными проверками | 20–35 рабочих дней, примерно 4–7 недель | Средняя |
| Все 18 источников для текущих функций приложения | 50–90+ рабочих дней, примерно 2,5–4,5+ месяца | Низкая до проверки журналов каждого источника |

Для варианта с тремя источниками ориентировочная разбивка: сервис и интеграция 1–2 дня; общий индекс/время/обновления 4–6; Claude 3–5; Codex 5–9; Gemini 1–3; цены 3–5; миграция и сквозная проверка 3–5. Пограничные форматы и отсутствие реальных примеров могут увеличить оценку. Демонстрация на одном простом файле получится значительно быстрее, но не подтверждает готовность к замене.

**Как проверять корректность**

- Ручные ожидаемые результаты для границ дня, UTC и локального пояса, переходов летнего времени и сессий, пересекающих полночь.
- Повторы, копии журналов, подагенты, forks, архивы, накопительные счётчики и смены модели/тарифа.
- Инвариант: полное чтение и обновление через индекс дают одинаковый результат; пересчёт после усечения/замены файла не удваивает токены.
- Незавершённая строка, повреждённый файл и ошибка доступа дают диагностируемое состояние, а не ложный ноль за весь день.
- Офлайн-первый запуск, недоступный каталог цен, неизвестная модель и пересчёт после обновления тарифа.
- Сравнение с исходными событиями и корректными отдельными отчётами ccusage. Общий session-отчёт нельзя использовать как единственный эталон из-за уже подтверждённой ошибки дат.
- Чистый Mac без Node/npm/ccusage: запуск приложения, обновления, история, виджет, выбор нестандартных папок. Замер холодного и повторного прохода на крупных журналах; численное ускорение пока не измерялось.

**Рекомендация при самостоятельной реализации сборщика**

Для полной независимости рекомендую Swift-реализацию, сначала для Claude, затем Codex и Gemini. Выпуск с тремя источниками должен явно перечислять поддерживаемые агенты; удаление CLI при сохранении обещания «все источники» требует завершить остальные адаптеры. Отдельные алгоритмы и тестовые случаи ccusage полезны как основа, но подтверждённые ошибки нельзя переносить вместе с ними.

После перехода пользователь устанавливает только `.app`. Внешний CLI и Node не требуются; сетевые обращения остаются лишь для необязательного обновления цен. Ответственность за новые форматы журналов и модели переходит к нам. Для трёх источников это контролируемый объём сопровождения, для восемнадцати — самостоятельное направление разработки.

Если задача ограничивается удобством установки, есть более дешёвый отдельный вариант: встроить нативный helper в `.app` и зафиксировать исправленную версию. Это убирает пользовательскую установку CLI и Node, но сохраняет кодовую зависимость от ccusage и не удовлетворяет требованию полностью собственного сборщика.

**Уточнение: включение исходников ccusage в приложение**

После уточнения задачи — разрешено использовать исходники ccusage, требуется убрать отдельную установку — рекомендую именно встроенный компонент, собранный из закреплённой копии исходников. Предыдущие оценки 20–35 дней для трёх источников относятся к самостоятельной реализации и к этому варианту не применяются.

В исследованной v20.0.26 вычислительная часть написана на Rust. npm-пакет содержит launcher для платформенного исполняемого файла; для нашей поставки он не нужен. Исходники можно хранить в `Vendor/ccusage`, собирать Cargo во время сборки приложения и включать результат в `LLM Usage.app/Contents/MacOS/ccusage`. Rust, Cargo, Node и отдельная установка ccusage на компьютере пользователя не требуются. Rust нужен разработчику и CI.

Это включение кода в наш продукт, хотя он исполняется отдельным процессом внутри установленного приложения. Сохраняются готовые адаптеры, расчёт цен, JSON-контракт и изоляция сбоев. Факт копирования исходников не устраняет ограничения и ошибки самого ccusage.

| Способ | Изменения | Предварительная оценка |
|---|---|---|
| Исходники → встроенный исполняемый файл | Cargo в сборке, упаковка и подпись, запуск по пути внутри bundle | 1–2 дня на прототип; 3–7 рабочих дней на подготовку к выпуску |
| Исходники → библиотека внутри основного процесса | Собственная граница Rust–Swift, C ABI/обёртка, управление памятью, ошибки и отмена | Ориентировочно 1–3 недели |
| Самостоятельный Swift-сборщик | Новые парсеры, цены, агрегация, индекс и проверка совместимости | Прежняя оценка: 20–35 дней для Claude, Codex и Gemini |

Оценки для одного разработчика; сборка прототипа в рамках исследования не выполнялась. Вариант с библиотекой не даёт дополнительного удобства установки пользователю. В проверенных манифестах есть Rust-crates и CLI `[[bin]]`, но нет готовой поставки библиотеки с интерфейсом для Swift; простое добавление `.rs` в Swift-проект не подходит.

Для встроенного исполняемого файла нужны следующие изменения:

1. Закрепить версию исходников, `Cargo.lock` и Rust toolchain. Сохранить MIT-уведомления и учесть лицензии включённых зависимостей и данных. Переносить нужно также ресурсы и файлы сборки, а не только `.rs`.
2. Передавать фиксированный снимок цен через `CCUSAGE_PRICING_JSON_PATH`. `ccusage-core/build.rs` требует этот файл либо специальную возможность скачать его при сборке. Версию CLI можно передать через `CCUSAGE_VERSION`, иначе его build script читает корневой `package.json`. Наличие этого JSON не означает необходимость Node.
3. Добавить сборку Cargo и копирование helper в `Scripts/build-local.sh`, подписать его перед внешним bundle, обновить проверку поставки и CI. Собирать для архитектур, которые поддерживает само приложение.
4. В `CCUsageService` заменить поиск внешнего CLI на путь внутри приложения. Сохранить `ProcessRunner`, декодер и обработку таймаутов; убрать обязательность пути и диагностики установленного CLI из настроек. Виджет продолжает читать снимки.
5. Внести небольшой сопровождаемый патч для дат Claude: фильтровать исходные события нужным диапазоном до агрегации. После проверки общего отчёта это позволит убрать дополнительный Claude-запрос в режиме всех агентов. Включение неизменённого upstream само по себе два запроса не отменяет.
6. Проверить чистый Mac без Node/npm/ccusage, офлайн-запуск, ошибки чтения журналов, даты и сессии через полночь, подпись и запуск вложенного файла. Проверить существующие режимы обновления, историю и виджет.

Сборка и обновление заимствованного кода станут нашей ответственностью: новую версию upstream нужно явно перенести, совместить с локальными исправлениями и проверить. Пользовательские установки и различия версий CLI исчезнут. Автоматического ускорения чтения журналов этот перенос не обещает — алгоритмы останутся прежними.

**Границы исследования:** подробно изучены Claude, Codex, Gemini, общие загрузка/цены и интеграция приложения; OpenCode, Antigravity, Hermes и Copilot проверены как примеры дополнительных форматов.
